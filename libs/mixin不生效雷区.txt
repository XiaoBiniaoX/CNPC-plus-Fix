在 1.12.2 使用 **MixinBooter**（尤其是高版本的 `10.7`）是目前开发低版本 Forge 的最优解。它通过集成 `SpongePowered Mixin` 并作为 Early Tweaker 加载，帮你解决了很多原生 1.12.2 配置 Mixin 的黑魔法。

但即便如此，1.12.2 的类加载机制极其脆弱，你依然会面临一堆由于“加载顺序”、“环境隔离”和“混淆”导致的致命雷区。

以下是完整的配置方法以及你需要死死踩住的 **1.12.2 Mixin 专属雷区列表**。

---

## 🛠️ 1.12.2 MixinBooter 核心配置步骤

要让 Mixin 真正生效且在开发环境（IDEA）和生产环境（Jar）都能跑通，你的 `build.gradle` 和 `MixinConfig` 必须严格配置。

### 1. `build.gradle` 配置

在 1.12.2 配合 MixinBooter，你**不需要**在 gradle 里引入古老的 `mixin-gradle` 插件，直接作为编译依赖引入即可。

```groovy
repositories {
    maven { url = "https://maven.cleanroommc.com/" } // MixinBooter 仓库
}

dependencies {
    // 引入 MixinBooter 作为编译和运行依赖
    deobfCompile "zone.skwrl.mixinbooter:MixinBooter:10.7"
    
    // 如果你本地没有加入 mixin 核心，可以单独以 compileOnly 引入 annotationProcessor
    annotationProcessor 'org.spongepowered:mixin:0.8.5:processor'
}

// 极其重要：确保注解处理器能找到你的 mixin 配置文件
compileJava {
    options.compilerArgs += [
        '-ArefMapNotSavedUndecorated=true',
        '-AoutRefMapFile=${project.buildDir}/resources/main/mixins.${modid}.refmap.json'
    ]
}

```

### 2. 在代码中注册（MixinBooter 的核心用法）

使用 MixinBooter 10.7，你**不要**去写 `IEarlyMixinLoader` 接口，也不要去动 `MANIFEST.MF`。
你只需要写一个普通的类，实现 MixinBooter 提供的一个**普通接口**即可：

```java
import zone.skwrl.mixinbooter.ILateMixinLoader;
import java.util.Collections;
import java.util.List;

// 必须放在一个“绝对不会被提前加载”的包里
public class MyModMixinLoader implements ILateMixinLoader {
    @Override
    public List<String> getMixinConfigs() {
        // 返回你的 mixins.json 文件名
        return Collections.singletonList("mixins.mymod.json");
    }
}

```

然后在你的 `mcmod.info` 或者对应的加载声明里确保 MixinBooter 能扫描到它。

## ⚠️ 1.12.2 MixinBooter 10.7 专属雷区（死活不生效、崩溃的原因）

### 雷区一：类提前加载（Class Circus）—— 1.12.2 第一大死因

**【现象】** 游戏报错 `Class X was loaded before target X could be transformed` 或者 Mixin 直接毫无反应。
**【原因】** 1.12.2 的 Forge 启动时，如果你的 `ILateMixinLoader` 类、或者你的主 Mod 类、或者任何事件监听类，在 Mixin 注入之前**不小心触发了对目标类（比如 `EntityNPCInterface`）的引用**，JVM 就会把这个类先加载进内存。
一旦类被加载，Mixin 就**永远无法再修改它**。
**【踩雷避险】**

* **绝对不要**在你的 `ILateMixinLoader` 实现类里写任何 `import` 目标 Mod 类的代码。
* 保持 MixinLoader 极其干净，它只负责返回一个字符串列表（Json 文件名）。
* 绝对不要在 `FMLPreInitializationEvent` 之前去碰任何会被 Mixin 的类。

### 雷区二：开发环境（IDE）生效，打包成 Jar 后不生效

**【现象】** 在 IDEA 里测试一切正常，NPC 行为被成功修改。打包放进服务器/客户端后，Mixin 犹如人间蒸发。
**【原因】** **Refmap 混淆丢失**。
在 IDEA 里，类名是未混淆的（`net.minecraft.entity.EntityLivingBase`）。打包后，原版类名变成了混淆名（`vp`）。如果你的 `mixins.mymod.refmap.json` 没有被正确生成或者没有被打包进 Jar 的根目录，Mixin 在线上环境就找不到目标方法。
**【踩雷避险】**

* 检查打包后的 Jar 文件，看看根目录下有没有 `mixins.mymod.refmap.json`。
* 检查你的 `mixins.mymod.json` 里面有没有写 `"refmap": "mixins.mymod.refmap.json"`。

### 雷区三：与遗留 CoreMod / Tweaker 的撞车冲突

**【现象】** 加上 MixinBooter 后，游戏在启动时报 `LaunchPlugin` 冲突，或者其他带 CoreMod 的 Mod（比如某些旧版优化 Mod）直接崩掉。
**【原因】** MixinBooter 10.7 使用了较新的类加载拦截机制。1.12.2 的很多老 Mod 还在用 `ClassTransformer` 自行修改字节码。如果对方先改了，Mixin 可能会因为找不到原本的方法签名而崩溃；如果 Mixin 先改了，对方的 ASM 可能会因为找不到原本的字节码特征而崩溃。
**【踩雷避险】**

* 如果目标类（如 CNPC）同时被你写的 ASM 和你的 Mixin 盯着，**二选一**。既然用了 MixinBooter，建议把原先痛苦的 ASM 全部重写为 Mixin。
* 如果必须共存，确保 Mixin 永远在传统 ASM 之后执行（MixinBooter 的 `ILateMixinLoader` 就是为了这个设计的，它会尽量靠后加载）。

### 雷区四：`@Shadow` 变量在混淆环境崩溃

**【现象】** 在 Mixin 里面 `@Shadow` 了原版或者其他 Mod 的字段/方法，结果报 `NoSuchFieldError`。
**【原因】** 对于原版 Minecraft 的字段（比如 `Entity#isDead`），由于有 `SRG` 映射，Mixin 会自动处理。但如果你 `@Shadow` 的是 **CustomNPCs 内部的私有字段**，CNPC 在生产环境是**没有 SRG 混淆的（它是二方/三方Mod）**。
如果你在 shadow 别人口里的字段时，不小心被混淆工具（如 `Srg2Mcp`）误伤改了名，就会找不到。
**【踩雷避险】**

* 对付 CustomNPCs 这种第三方 Mod，如果需要调用它的私有成员，**不要瞎用 `@Shadow**`。
* 推荐直接在 Mixin 类里使用 **`Accessors`（访问器）** 或者是动态反射。
* 如果非要 shadow，对于非原版类，确保设置 `remap = false`：
```java
@Shadow(remap = false)
private int respawnTicks; // 显式声明不进行重混淆映射

```



### 雷区五：Mixin 内部写了 Lambda 表达式导致报错

**【现象】** 在 Mixin 的方法体（比如 `@Inject` 内部）写了 `list.forEach(x -> ...)` 或者复杂的 Stream 流，游戏崩溃提示 `ClassFormatError: Invisible parameter count`。
**【原因】** 1.12.2 运行在 Java 8 环境。Java 8 的 Lambda 表达式会在编译时动态生成类似 `lambda$mymethod$0` 的合成方法（Synthetic Method）。Mixin 在动态织入（Transform）字节码时，对这些合成方法的处理非常脆弱，经常导致目标类结构损坏。
**【踩雷避险】**

* 在 1.12.2 的 Mixin 代码块内部，**老老实实写标准的 For 循环和匿名内部类**，克制住写 Lambda 和 Stream 的冲动。

### 💡 避坑总结 checklist

1. 检查 `mixins.json` 里的 `package` 配置，确保 Mixin 类和普通的 Mod 注册类**绝对不在同一个包下**。
2. 每一个 `@Inject` 都要加上 `remap = false`（针对 CNPC 的类）或 `remap = true`（针对 Minecraft 原版的类）。
3. 遇到不生效，第一时间在启动参数加上 `-Dmixin.debug.export=true`，去运行目录下的 `.mixin.out` 文件夹直接看反编译出来的成型字节码，到底有没有把你的代码塞进去。


在 1.12.2 使用 MixinBooter 10.7 搞底层修复，除了前面提到的那些，还有几个隐藏极深、能让你排查几天几夜都找不出原因的**终极雷区**。

这几个雷区大多和 **1.12.2 特有的 Forge 动态修改机制** 以及 **第三方 Mod 的黑魔法** 有关：

---

### 雷区六：`@Redirect` 与别的 Mod 迎头相撞（导致火拼崩溃）

**【现象】** 你的补丁在单体测试时完美运行，但放到玩家的整合包里，游戏在主菜单加载前直接崩溃，提示某个原本存在的方法找不到了。
**【原因】** 你在 Mixin 中使用了 `@Redirect` 拦截了某个方法调用（例如拦截了 NPC 死亡时的属性同步）。而整合包里的另一个优化 Mod（如 *Gasoline* 或某个性能修复 Mod）正好也用 Mixin 或 ASM 修改了**同一个方法调用**。
`@Redirect` 会直接修改字节码中的调用指令（`INVOKEVIRTUAL` 等）。如果两个 Mod 都想 `@Redirect` 同一个地方，后加载的那一个就会因为**找不到原始指令**而直接让游戏暴毙。
**【踩雷避险】**

* **尽量禁用 `@Redirect**`。
* 改用 `@Inject(at = @At("INVOKE", target = "..."), cancellable = true)`。在目标方法执行前进行拦截、改写变量、然后 `ci.cancel()`，这种方式的兼容性比 `@Redirect` 高一万倍。

---

### 雷区七：CNPC 的动态代理类（Proxy）导致 Mixin 目标“失踪”

**【现象】** 你满心以为 Mixin 挂载到了 `EntityNPCInterface` 或者 `Container` 上，但进游戏发现部分特定的 NPC（比如启用了某些特定 AI 或脚本的 NPC）依然会触发死亡抽搐，你的 Mixin 根本没拦截到它们。
**【原因】** CustomNPCs 内部为了处理脚本系统（Java 1.12.2 用的 Nashorn 引擎），在某些地方使用了动态代理（Dynamic Proxy）或动态生成子类。
当游戏运行中产生一个动态子类时，它继承自 `EntityNPCInterface`，但它的类名可能是 `EntityNPCInterface$$EnhancerBySpring$$...`。如果你把 Mixin 织入到了非虚方法（`private` 或 `final`）中，子类在调用时可能会绕过你的拦截。
**【踩雷避险】**

* 确保你 `@Inject` 的目标方法是原版就有的**虚方法**（如 `onUpdate`, `onDeath`, `readEntityFromNBT`），这些方法在子类调用时一定会走多态流程，从而触发你的 Mixin。
* 尽量避免去 Mixin 那些 CNPC 自己独创的、且没有被子类重写的私有工具方法。

---

### 雷区八：`@ModifyVariable` 索引漂移（1.12.2 的大杀器）

**【现象】** 你想用 `@ModifyVariable` 去修改 `onCraftMatrixChanged` 里面的局部变量（比如修改循环的边界值或者算出来的配方结果），在 IDEA 里跑得好好的，打包出去直接报 `Invalid descriptor` 或者是改错了变量，导致游戏奇葩崩溃。
**【原因】** 局部变量（Local Variable）在字节码中是靠索引（`index = 1`, `index = 2`）来定位的。
在 1.12.2 生产环境下，由于代码经过了混淆和 Forge 的 `Binpatches` 重新编排，**局部变量的实际索引顺序极有可能发生改变**。你在开发环境看到配方变量是 `index = 3`，到了线上它可能变成了 `index = 4`，导致你的 Mixin 强行修改了不该修改的数据。
**【踩雷避险】**

* 玩 1.12.2 Mixin 尽量**少用** `@ModifyVariable`。
* 如果非要改局部变量，推荐使用 `@Inject` 配合 `At(value = "STORE", target = "...")`，去拦截变量被赋值（Store）的那一刻，或者干脆用 `@At("HEAD")` 直接拦截并接管整个方法（使用 `cancellable = true` 并自己重写该段逻辑）。

---

### 雷区九：`FMLCorePluginContainsFMLMod` 的影子清单雷区

**【现象】** 在 MixinBooter 10.7 环境下，如果你把 Mixin 的引导类和你的主 Mod 核心（CoreMod）塞进了同一个 Jar 包，服务器启动时报 `Jar Checksum` 错误或直接拒绝加载你的 Mod。
**【原因】** 1.12.2 的 Forge 对包含 CoreMod 的 Jar 包有一套严格的清单（`MANIFEST.MF`）检查机制。如果你在 `MANIFEST.MF` 里声明了 `FMLCorePlugin`，Forge 会在极度早期用特殊的 `LaunchClassLoader` 去剥离这个 Jar。如果你的 Mixin 注册逻辑触发得太早，会导致整个 Jar 被过早锁定，引发后续的正常 Mod 注册组件（如 `@Mod` 注解）直接失效。
**【踩雷避险】**

* 既然用了 MixinBooter 10.7，**完全不需要在 `MANIFEST.MF` 里写任何关于 Mixin 的 Tweaker 声明**。
* 只需要按照 MixinBooter 的标准，提供一个普通的 `ILateMixinLoader` 实现类，让 MixinBooter 去发现它。把主导权彻底交给 MixinBooter，不要和老旧的 CoreMod 声明混用。

---

### 雷区十：客户端/服务端（Side）隔离崩溃

**【现象】** 客户端测试完全没有问题，合成台能用了，NPC 也不抽搐了。一放到 1.12.2 纯净服务端（Dedicated Server）里，开服直接弹 `NoClassDefFoundError: net/minecraft/client/...`。
**【原因】** CustomNPCs 里面有海量的 GUI 和渲染代码。你在写 Mixin 时，如果顺手 `@Shadow` 或者 `import` 了目标类里的某个客户端独有变量（比如 `GuiNPCInterface` 或 `ModelRenderer`），这些类在纯服务端（Server）里是**被 Forge 彻底物理阉割掉的**。一旦服务端 JVM 尝试加载你的 Mixin 类，发现找不到这些客户端类，就会直接炸服。
**【踩雷避险】**

* 永远保持警惕：如果这个 Mixin 目标方法（如死亡复活逻辑、全局合成逻辑）是双端都要跑的，**在 Mixin 类里绝对不能出现任何 `net.minecraft.client` 下的类和方法**。
* 如果必须要动和渲染/GUI 相关的代码，在 `mixins.json` 里单独开一个 `client` 数组，指定该 Mixin 文件**仅在客户端加载**：
```json
"client": [
    "client.MixinNPCGui"
]

```



```

### 💡 绝招：善用 Mixin 的“手术刀”配置
在 1.12.2 调 Mixin，如果遇到了莫名其妙的不生效或崩溃，记住这个终极自救参数。在你的 IDEA 运行配置（Run Configuration）的 **VM Options** 里加上：
```text
-Dmixin.debug.verbose=true
-Dmixin.debug.export=true

```

* `verbose=true` 会在控制台巨细靡遗地印出每一条 Mixin 的织入轨迹。如果它被别的 Mod 顶掉了，或者因为没有 remap 失败了，控制台会用黄字或红字明明白白写出来。
* `export=true` 会在你的游戏运行目录下生成一个 `.mixin.out` 文件夹。里面是**Mixin 织入完成后、最终形态的 .class 文件**。用 IDEA 直接把这里面的 class 拖进去反编译，你就能像看普通 Java 代码一样，一眼看出你的代码到底有没有成功塞进 CNPC 里面、里面的变量有没有改对。

1.12.2 确实像个随时会炸的雷区，但只要摸清了它的脾气，用 Mixin 绝对能把 CNPC 这个陈年老 Mod 安排得明明白白！
